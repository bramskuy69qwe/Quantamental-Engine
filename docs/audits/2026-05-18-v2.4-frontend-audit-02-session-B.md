## Findings

### [FE-HIGH-008] [Data] Regime Backfill fails at 80% with backend AttributeError

  Description: On the Regime Backfill tab, clicking "Start Backfill" with the default form (MODE: Macro Only, FROM 01/01/2020, TO 19/05/2026) triggers a real backfill process. Progress bar appears below the button and advances. At ~80% the process errors out with the message `'RegimeFetcher' object has no attribute 'close'` — surfaced in two places: (1) a red toast top-right of the page, (2) below the form alongside the stuck 80% progress bar.

  Evidence: Screenshot ss_0653fgbca shows both the toast (`Backfill failed: 'RegimeFetcher' object has no attribute 'close'`) and the inline progress bar at 80% with the same error caption. Subsequent Overview check (ss_36678ndsx) confirms the two empty cards (BTC Market Cap, Aggregate OI Change) still show "Not yet backfilled" after the failed run. The signal coverage table on Backfill (ss_2630gbf8r) confirms both signals show 0 rows / Not backfilled.

  Impact: The backfill feature is broken. The two signals that the Overview tab explicitly directs users to backfill (via the "Use Backfill tab" CTAs) cannot be backfilled through the UI. Backend AttributeError — `'RegimeFetcher' object has no attribute 'close'` — likely a missing `__exit__` or `close()` cleanup method on a context manager / resource handler.

  Recommended fix: Backend — add the missing `close()` method to `RegimeFetcher` (or remove the `.close()` call from whatever code path attempts it). Frontend — once the backend is fixed, the existing toast + progress UI behaves correctly and would show successful completion. After a successful backfill, the Overview's two "Use Backfill tab" cards should auto-update; if they don't, that's a follow-up finding to file.

  Effort: Small (single missing method or removed cleanup call on backend) + verification pass after fix.

### [FE-MED-021] [Data] Backfill page mixes DD/MM/YYYY and YYYY-MM-DD date formats

  Description: On Regime Backfill, the FROM/TO date inputs in the left form display dates as `01/01/2020` and `19/05/2026` (DD/MM/YYYY, European style). The signal coverage table on the right displays dates as `2015-01-02`, `2026-05-18` (YYYY-MM-DD, ISO 8601). Same date semantics, two different formats, same page.

  Evidence: Screenshot ss_2630gbf8r — left form shows `01/01/2020` and `19/05/2026`; right table SOURCE column shows `2015-01-02`, `2026-05-18`, etc.

  Impact: User has to mentally reconcile two formats. Especially confusing for ambiguous dates (`05/06/2026` = May 6 or June 5?). YYYY-MM-DD is unambiguous and is already used elsewhere in the engine (History page, Pre-Trade Log, etc.).

  Recommended fix: Standardize on YYYY-MM-DD throughout. The form's date inputs can still accept either format on input (browser native handling) but should display in ISO format consistent with the rest of the engine.

  Effort: Small.

### [FE-MED-023] [UX] Regime "Config" tab is read-only — no edit/save UI despite the label

  Description: The Regime Config sub-tab shows current classifier thresholds (VIX Panic 30, HY Spread Panic 5, etc.) and decision tree rules (color-coded). The values are displayed but appear non-editable — no input fields, no Save button. The only interactive control is "Reclassify All Dates" at the bottom of the threshold list. The tab is named "Config" but offers no configuration capability.

  Evidence: Screenshot ss_5596zhmvo — values displayed as static numbers; no input affordances on any threshold row.

  Impact: User clicks "Config" expecting to change settings, finds a read-only reference page. Misleading. Either the thresholds should be editable (with Save / Reset / validation), or the tab should be renamed to "Classifier Rules" or "Rule Reference" so expectations are set.

  Recommended fix: Two options:
  - **Make editable**: add input fields for each threshold + a single Save button at the bottom. Probably requires backend support (a writable config endpoint) which audit-01 noted doesn't currently exist for these.
  - **Rename + clarify**: keep read-only, rename tab to "Classifier Rules" or "Reference", add a note explaining where the values come from (config file, env, etc.) and how to edit them.

  Effort: Small (rename) to medium (full edit UI + backend).

### [FE-MED-025] [Architecture] Backtest Run uses Date Range; Backtest Fetch Data uses Days Back

  Description: Both tabs ask the user "how far back to look", but use different paradigms:
  - **Run** tab: DATE RANGE picker `2026-02-18 → 2026-05-19` with quick chips `1Y / 6M / 3M / 1M`.
  - **Fetch Data** tab: numeric field DAYS BACK `730`.

  Same conceptual question, two different UX surfaces.

  Evidence: Run screenshot ss_1436dw00t (Date Range + chips); Fetch Data screenshot ss_7480q8xus (just a Days Back number).

  Impact: User has to context-switch when moving between tabs. Fetch Data requires mental math (how many days is "3M" → 90). Run requires picking explicit dates (more steps for a quick fetch).

  Recommended fix: Pick one. Date range is more flexible and human-readable; Days Back is faster for "show me the last N days". Reasonable compromise: both tabs offer Date Range with the same quick chips, AND a small "as days back" tooltip on the chips for users who think in days. Or: standardize on Date Range and remove Days Back.

  Effort: Small.

### [FE-MED-026] [Architecture] Backtest Models tab duplicates Run tab's strategy fields

  Description: The Backtest Models tab has fields for EMA FAST, EMA SLOW, ATR SL MULT, ATR TP MULT, MIN ATR-C, DIRECTION, RISK/TRADE, MAX POSITIONS — exact same parameter set the Run tab also exposes. The Models tab adds MAX EXPOSURE, MAX VIX, REGIME MULTIPLIER fields that Run doesn't have. The Run tab has a LOAD MODEL dropdown (currently "— Custom —") that presumably loads saved Models.

  This means: the same strategy parameters are configured in two places. The relationship between Models tab (save preset) and Run tab (Load Model dropdown + override) isn't documented in the UI.

  Evidence: Run screenshot ss_1436dw00t (Strategy Config form); Models screenshot ss_2157669rq (same fields plus MAX EXPOSURE / REGIME).

  Impact: User has to learn the model — is the Run form a "free run" that doesn't save? Does saving a Model and then editing in Run create a new model? Are the Run-only fields a subset of Models that always override? Without documentation, hard to know.

  Recommended fix: Either (1) collapse the duplication — make Run tab's form ONLY a "Load Model + Run" flow with non-editable fields once a model is loaded; if user wants to tweak, they save a new model first. Or (2) keep the duplication but add a clear visual indicator on Run that says "These values match Model X" / "Custom (not saved)". And expose all 11 model fields on Run tab so the parameters fully match what a saved Model is.

  Effort: Medium (architectural cleanup).

## Cross-cutting observations

**The Backfill failure is the only "real bug" surfaced this session — but the surrounding UX handles it well.** A backend AttributeError shouldn't be surfaced as raw exception text in a user-facing toast — ideally the toast would say something like "Backfill couldn't complete. Check the engine log for details." — but the fact that the engine *does* surface the failure (red toast + inline progress-bar message + stopped progress at 80%) is a substantial UX improvement over what Session A's FE-HIGH-007 was warning about. The Task 108 htmx error handler has clearly been extended to surface 5xx-style failures visibly, and that progress is worth recording.

**Designed empty states are now the norm on Analytics and several other surfaces.** Saw three more this session: Models' "No models defined. Create one using the form." (actionable); Fetch Data's "No jobs yet." (concise); Recent Regime Changes section of Overview (table with real rows). Combined with Analytics' R-Multiples / Risk Metrics designed states, the engine has enough exemplars now to template the EmptyState primitive. The remaining inconsistent empty states (Config page "Select an account..." from audit-01, Calendar PnL future cells) should be the next ones brought into line.

**Two surfaces still use the read-only-display-named-Config anti-pattern.** Regime Config (this session) is read-only thresholds with no save. Looking back at audit-01, the original Configuration → Accounts page had similar issues (placeholder "Select an account..." with broken interaction). The naming-vs-behavior gap is consistent: "Config" tabs should either offer editing or be renamed.

**Source/provider casing inconsistency is becoming a pattern.** Audit-01's LOW-005 was about provider name casing in Connections. This session's FE-LOW-014 is about source casing on Backfill. Each surface canonicalizes (or doesn't) independently. A single `format_provider(name)` helper applied across Connections, Backfill, and probably the Backtest Models LOAD MODEL dropdown would close the variant.

**The page-level period selector / nested-navigation pattern is now confirmed on five surfaces.** Audit-01 (Regime Overview), Session A' (Equity Curve, Calendar PnL), this session (Backfill has its own date range picker + the Regime page header could be read as period selector inheritance, though it doesn't apply on Backfill). The PeriodSelector primitive remains the single highest-leverage refactor in the queue.

## Open questions for operator

1. **`'RegimeFetcher' object has no attribute 'close'` — is this a known issue?** It's the most concrete bug this session surfaced. Backend triage needed: missing method, or removed cleanup call that should still be there. The Regime backfill feature is currently unusable for the two signals that need it most (BTC Market Cap, Aggregate OI Change).

2. **Should error toasts wrap raw exception strings?** The toast surfaced `'RegimeFetcher' object has no attribute 'close'` verbatim. Functional for a developer debugging; jarring for an end-user. Product decision: surface raw technical detail always (good for solo-operator tools), or wrap in friendlier prose with a "show details" expand (better for any future multi-user scenario).

3. **Regime Config tab — keep read-only or make editable?** Current state is misleading. Decision feeds into the rename-vs-add-editing fix in FE-MED-023.

4. **Backtest Models vs Run duplicated parameters — what's the intended workflow?** Save-Model-then-Load-in-Run vs free-form-Run-without-saving — both currently work but the relationship isn't documented in the UI. FE-MED-026 needs an architectural decision before the fix can be scoped.

5. **Does the engine support importing/exporting saved Models?** Not visible in the UI. Could matter for multi-machine setups or sharing model definitions.

6. **News feed pagination — is there one?** Scrolled through many items; no "Showing N of M" or "Load more" was visible. Either it's infinite scroll, or there's a hard cap. Worth confirming so a user knows the boundary of what's being shown.

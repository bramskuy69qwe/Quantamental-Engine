## Findings

### [FE-HIGH-008] [Data] Regime Backfill fails at 80% with backend AttributeError

  Description: On the Regime Backfill tab, clicking "Start Backfill" with default form (MODE: Macro Only, FROM 01/01/2020, TO 19/05/2026) triggers a real backfill. Progress bar advances. At ~80% it errors with `'RegimeFetcher' object has no attribute 'close'` — surfaced in two places: (1) a red toast top-right, (2) below the form alongside the stuck 80% progress bar.

  Evidence: Screenshot ss_0653fgbca shows both the toast and inline progress bar with same error caption. Subsequent Overview check (ss_36678ndsx) confirms the two empty cards (BTC Market Cap, Aggregate OI Change) still show "Not yet backfilled" after the failed run. Signal coverage table on Backfill (ss_2630gbf8r) confirms both signals show 0 rows / Not backfilled.

  Impact: Backfill feature is broken. The two signals the Overview directs users to backfill via "Use Backfill tab" CTAs cannot be backfilled through the UI. Backend AttributeError — likely a missing `__exit__` or `close()` cleanup method on a context manager / resource handler.

  Recommended fix: Backend — add the missing `close()` method to `RegimeFetcher` (or remove the `.close()` call). Frontend — once backend is fixed, existing toast + progress UI behaves correctly. After successful backfill, Overview's two "Use Backfill tab" cards should auto-update; if they don't, that's a follow-up.

  Effort: Small (single missing method or removed cleanup call) + verification pass.

### [FE-MED-021] [Data] Backfill page mixes DD/MM/YYYY and YYYY-MM-DD date formats

  Description: On Regime Backfill, FROM/TO date inputs display dates as `01/01/2020` and `19/05/2026` (DD/MM/YYYY, European). Signal coverage table on right displays dates as `2015-01-02`, `2026-05-18` (YYYY-MM-DD, ISO 8601). Same date semantics, two different formats, same page.

  Evidence: Screenshot ss_2630gbf8r — left form shows `01/01/2020`; right table SOURCE column shows `2015-01-02`, `2026-05-18`, etc.

  Impact: User has to mentally reconcile two formats. Confusing for ambiguous dates (`05/06/2026` = May 6 or June 5?). YYYY-MM-DD is unambiguous and already used elsewhere in the engine.

  Recommended fix: Standardize on YYYY-MM-DD throughout. Form inputs can still accept either format on input (browser native) but display in ISO consistent with rest of engine.

  Effort: Small.

### [FE-MED-023] [UX] Regime "Config" tab is read-only — no edit/save UI despite the label

  Description: The Regime Config sub-tab shows current classifier thresholds (VIX Panic 30, HY Spread Panic 5, etc.) and decision tree rules (color-coded). Values are displayed but appear non-editable — no input fields, no Save button. Only interactive control is "Reclassify All Dates". Tab is named "Config" but offers no configuration capability.

  Evidence: Screenshot ss_5596zhmvo — values displayed as static numbers; no input affordances.

  Impact: User clicks "Config" expecting to change settings, finds read-only reference page. Misleading. Either thresholds should be editable (with Save / Reset / validation), or tab should be renamed to "Classifier Rules" or "Rule Reference".

  Recommended fix: Two options:
  - **Make editable**: add input fields for each threshold + single Save button. Probably requires backend support (a writable config endpoint).
  - **Rename + clarify**: keep read-only, rename to "Classifier Rules" or "Reference", add a note explaining where values come from and how to edit.

  Effort: Small (rename) to medium (full edit UI + backend).

### [FE-MED-025] [Architecture] Backtest Run uses Date Range; Backtest Fetch Data uses Days Back

  Description: Both tabs ask "how far back to look" but use different paradigms:
  - **Run** tab: DATE RANGE picker `2026-02-18 → 2026-05-19` with quick chips `1Y / 6M / 3M / 1M`.
  - **Fetch Data** tab: numeric field DAYS BACK `730`.

  Same conceptual question, two different UX surfaces.

  Evidence: Run screenshot ss_1436dw00t; Fetch Data screenshot ss_7480q8xus.

  Impact: User context-switches between tabs. Fetch Data requires mental math (how many days is "3M" → 90). Run requires picking explicit dates.

  Recommended fix: Pick one. Date range is more flexible and human-readable; Days Back is faster for "last N days". Reasonable compromise: both tabs offer Date Range with same quick chips, AND a small "as days back" tooltip. Or standardize on Date Range.

  Effort: Small.

### [FE-MED-026] [Architecture] Backtest Models tab duplicates Run tab's strategy fields

  Description: Backtest Models tab has fields for EMA FAST, EMA SLOW, ATR SL MULT, ATR TP MULT, MIN ATR-C, DIRECTION, RISK/TRADE, MAX POSITIONS — exact same parameter set Run also exposes. Models adds MAX EXPOSURE, MAX VIX, REGIME MULTIPLIER that Run doesn't have. Run has a LOAD MODEL dropdown (currently "— Custom —") that presumably loads saved Models.

  Same strategy parameters configured in two places. The relationship between Models (save preset) and Run (Load Model dropdown + override) isn't documented.

  Evidence: Run ss_1436dw00t; Models ss_2157669rq.

  Impact: User has to learn the model. Is Run a "free run" that doesn't save? Does saving a Model and then editing in Run create a new model? Are Run-only fields a subset of Models that always override?

  Recommended fix: Either (1) collapse the duplication — make Run tab's form ONLY a "Load Model + Run" flow with non-editable fields once a model is loaded; if user wants to tweak, they save a new model first. Or (2) keep duplication but add clear visual indicator on Run saying "These values match Model X" / "Custom (not saved)". Expose all 11 model fields on Run.

  Effort: Medium (architectural cleanup).

## Cross-cutting observations

**The Backfill failure is the only "real bug" surfaced this session — but the surrounding UX handles it well.** A backend AttributeError shouldn't be surfaced as raw exception text in a user-facing toast — ideally the toast would say something like "Backfill couldn't complete. Check the engine log for details." — but the fact that the engine *does* surface the failure (red toast + inline progress-bar message + stopped progress at 80%) is a substantial UX improvement over what Session A's FE-HIGH-007 was warning about. The Task 108 htmx error handler has clearly been extended to surface 5xx-style failures visibly.

**Designed empty states are now the norm on Analytics and several other surfaces.** Three more this session: Models' "No models defined. Create one using the form." (actionable); Fetch Data's "No jobs yet." (concise); Recent Regime Changes section of Overview (table with real rows). Combined with Analytics' R-Multiples / Risk Metrics designed states, the engine has enough exemplars to template the EmptyState primitive.

**Two surfaces still use the read-only-display-named-Config anti-pattern.** Regime Config (this session) is read-only thresholds with no save. Audit-01's Configuration → Accounts had similar issues. Naming-vs-behavior gap consistent: "Config" tabs should either offer editing or be renamed.

**Source/provider casing inconsistency is becoming a pattern.** Audit-01's LOW-005 was about provider name casing in Connections. This session's FE-LOW-014 about Backfill SOURCE column. A single `format_provider(name)` helper applied across Connections, Backfill, and probably Backtest Models LOAD MODEL dropdown would close the variant.

**Page-level period selector / nested-navigation pattern now confirmed on five surfaces.** Audit-01 (Regime Overview), Session A' (Equity Curve, Calendar PnL), this session (Backfill has its own date range picker). PeriodSelector primitive remains the single highest-leverage refactor.

## E2E-P4-001 — HIGH — Apply Preset is 100% broken in v3 (empty 500, every target)

**Symptom**: `POST /api/config/apply-preset` → HTTP 500 with an EMPTY body. No log
line, no JSON error. Reproduced on a quiet sandbox engine for BOTH the active and
the non-active account, every preset.

**Mechanism (investigated, not assumed)**: `account_registry.list_accounts()` is a
**coroutine function** (`core/account_registry.py:320`; the sync twin
`list_accounts_sync` sits right beside it at :325). `api/routes_config.py:101`
iterated it **without `await`**:
`known = {a["id"] for a in account_registry.list_accounts()}` →
`TypeError: 'coroutine' object is not iterable`. That raises OUTSIDE the route's
only try/except (which wraps `apply_preset`), so FastAPI returns a bare 500 — the
empty body is the tell.

**Blast radius**: the branch runs whenever `account_id` is present in the body, and
the v3 Config UI ALWAYS sends it (`pages-config.jsx:690` posts
`{preset, account_id: tgt.id}`). So the Apply Preset button never worked in v3 —
for any preset, any target, including the active account. The omit-`account_id`
path (legacy callers) was unaffected, which is why no earlier test caught it.

**Provenance worth noting**: the explicit-`account_id` branch IS the Meridian audit's
`config-2` fix ("configuring a second account before switching to it is a normal
workflow"). The remediation introduced this regression — a fix-shaped defect that
green tests never saw because no test posted an explicit target.

**Fix (shipped)**: `await account_registry.list_accounts()` — matching the sibling
route (`routes_accounts.py:158`). Pins: `tests/test_apply_preset_account_target.py`
(5), driving the route function directly with stubs — never the shared TestClient,
because apply-preset writes `account_settings` + `account_params`, which resolve to
the operator's LIVE data dir. One pin asserts the async/sync shape the bug turned on.

## Verified-correct behaviours (the sandbox's real yield)

- **Failed account switch rolls back cleanly.** A keyless account can never complete
  `activate` (`_reinit()` needs exchange credentials), so the route takes its
  documented rollback path: 500 + `set_active(old)` + rollback reinit. Verified:
  account 1 remained active, no pane crashed. *(First spec version asserted the
  switch would SUCCEED and mis-read the 500 as a finding — re-scoped to assert the
  failure contract, which is what a keyless sandbox can actually prove.)*
- **Engine death degrades truthfully.** With a loaded Dashboard, the engine was
  hard-killed: panes walked to `no network — engine unreachable` /
  `… · showing last data`, **zero error boundaries**, and a relaunch + reload
  cleared the tier. This is the assertion that was impossible against live.
- **Keyless regime backfill partially succeeds** (yfinance/Binance-public need no
  key; FRED/Finnhub signals stay `NOT BACKFILLED`) without crashing a pane.
- Connections add→list→remove, models create→delete, manual link (seeded candidate
  resolved 1/1), mark-unplanned, reclassify, and a no-op account save all
  round-trip correctly under the 200-body alert-sniff oracle.

## Harness defects fixed in-phase (5 — all mine, none the app's)

1. **Seeds went to the wrong store.** The engine's `DatabaseManager` reads trading
   tables from the LEGACY DB (`db._conn`, baked `config.DB_PATH`); the split's
   per-account files are resolver-routed residue. Seeding per-account left every
   door empty. → all trading seeds now target legacy.
2. **`accounts` UNIQUE(exchange, broker_account_id)**: an `INSERT OR REPLACE` for
   account 2 with the same broker id silently DELETED account 1. → distinct broker
   id + `OR IGNORE` + a post-seed assertion that both ids survive.
3. **Fixed sleeps instead of polling** — locators resolved against not-yet-settled
   panes (the inbox mounts on the 5 s lane). → `expect().toBeVisible()` everywhere.
4. **Unscoped `select` filter matched the NAV account picker** and fired a real
   account activation during the preset test. → pane-scoped.
5. **`getByPlaceholder(/api key/i).first()` typed into the FIRST provider card**
   (`bwe_news`), so the news WebSocket spent the session trying to connect to
   `e2e-fake-key`. → add-row scoped; connections table cleared.
   *Observation (not filed): an invalid URI in a connection makes the news WS
   error-loop indefinitely with no UI surface. Fail-loud in logs only.*
   Also: the close-reason handler sits on a titled `<span>` (`pages-history.jsx:250`),
   not the cell or the badge — `getByTitle('Set / edit the close reason')` is the hook.

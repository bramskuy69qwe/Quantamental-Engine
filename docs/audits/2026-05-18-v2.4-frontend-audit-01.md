## Overall Verdict

The engine looks like a serious trading dashboard built by someone who's actually used Quantower / TradingView. Information density is good, color semantics are mostly consistent (green=long/win, red=short/loss), and the multi-card history page does a lot of work without feeling cramped. It does not look AI-generated.

But it shows the seams of a single-person build: row component drift between Position/Order/Trade History, a missing card primitive that lets Analytics breathe weirdly while History tightens up, several "Not Set / not backfilled / undefined" empty states that each look different, and one **outright broken interactive** (account detail panel returns HTTP 500 silently). The Add Account flow exposes only Binance even though Bybit/MEXC adapters exist. And the header indicator near "Plugin" is ambiguous enough that the engine owner himself misread it as "engine offline" during this audit.

The dominant pattern: missing primitives. A Card primitive, a Row primitive, an EmptyState primitive, a StatusIndicator primitive, and a PeriodSelector primitive would resolve roughly half the medium findings. Build those before adding new features.

## Cross-Cutting Patterns

**Missing component primitives** is the single largest leverage point. The 5 self-found calibration findings + 9 of the 14 medium findings I captured here all point to the same root cause: there is no shared Card / Row / EmptyState / StatusIndicator / PeriodSelector. Each page rolls its own. Build the primitives, migrate page-by-page, get 14+ findings resolved for the cost of 5 component implementations.

**Empty states are not designed, they're emergent.** "No open positions." (Dashboard), "No sessions yet." (Backtest), "No sessions yet" (Backtest sessions card), "Select an account..." (Config), "Not yet backfilled — use Backfill tab" (Regime BTC Market Cap and OI Change cards), "—" (Calculator preview unpopulated), "awaiting calculation" (Calculator regime card). Seven different empty-state treatments. Some are centered text, some are inline text, some are placeholder labels in dropdowns. An EmptyState primitive with a tone (informational / actionable / error) and a slot for an action button would standardize this.

**Period selectors are repeated and not factored.** Regime page alone has at least three different period-selector implementations: page-level (Month/Week/Quarter/Year/30D/90D/All), Regime Timeline (Swim/Bars/Blocks/Heat/Stack + 30d/90d/1y/All), and per-Macro-Signal chart (30d/90d/1y/5y/All). Analytics has its own (Month/Week/Quarter/Year/30D/90D/All). History has yet another (Last 90 days / Last 30 days / Last 15 days / Last 7 days / Yesterday / Today). These don't all need the same choices, but they should share a PeriodSelector primitive with configurable options and a documented precedence rule for nested selectors.

**Status indicators are visually overloaded with no clear vocabulary.** "Plugin · OFF" with a red dot, "LIVE" tag, "Standalone" mode, green dot before Plugin, "Connected" / "Not Set" tags on Connections, the orange banner across every page. Each is correctly trying to communicate state, but together they form a soup. A StatusIndicator primitive with documented severity levels (success / warning / error / info / neutral) and consistent placement would clarify.

### [CRIT-001] [UX/Data] Configuration → Accounts: detail panel returns HTTP 500

  Description: Clicking the only existing account card on `/config` (Accounts tab) does nothing visible. The right-side detail panel stays at "Select an account..." placeholder.

  Evidence:
  - Console: `Response Status Error Code 500 from /fragments/account-detail/1` (htmx error handler, fired on both attempts at 18:14:23 and 18:14:39 local).
  - Network: `GET http://localhost:8000/fragments/account-detail/1` → statusCode 500.
  - Screenshot: ss_43293men4 (post-click, panel still shows placeholder).

  Impact: User cannot view or modify their account settings — including the link_window_seconds setting that v2.4's HIGH-027 work depends on. The fragment swap fails silently because htmx doesn't surface the 500 to the user. No toast, no error banner, no console output for a non-developer to notice.

  Recommended fix: (1) Get the server-side traceback (engine logs would have it — I couldn't isolate it from sandbox because of log file path differences). (2) Add an htmx `htmx:responseError` handler that surfaces 4xx/5xx swaps as a visible toast or banner — silent failure on a critical interactive is unacceptable.

  Effort: Small (probably a simple template-rendering bug on the server side) + small (htmx error handler is a one-time global add).

  Screenshots: ss_43293men4

### [HIGH-001] [UI] Header "Plugin OFF" indicator is misread as "engine offline"

  Description: The top-right area of the header reads `Account 1 (Binanc...) ▾  |  Standalone ▾  |  ◯ Plugin  ● OFF  +437ms  |  ⚙`. The word "OFF" floats free of the word "Plugin" — visually it parses as a separate column. The engine owner read this during the audit as "the engine is offline" before realising it was the plugin indicator. Also: the empty circle before "Plugin" is a decorative separator, but the red filled dot before "OFF" is a real status light, so the eye trains itself to read "two status lights" when there's really one.

  Aryo also surfaced a secondary aspect: the `+437ms` latency number appears stuck on the OFF state — the indicator was supposed to be showing a live ping/latency value the way the dashboard's `LATENCY 95ms` does, but it's currently overwritten by "OFF" text. The latency number and the connection state are competing for the same display slot.

  Evidence: Zoomed screenshot of header (ss_5224rm25o region 930-1308 × 0-40). Two distinct latency numbers visible on every page: `LATENCY 127ms` in status bar AND `+437ms` near Plugin OFF — different values, no documented relationship.

  Impact: Misreading "engine offline" on a trading dashboard is the worst class of UX bug. Even if the user knows the plugin is intentionally off, the visual primes anxiety. And the duplicated latency display means the user has to mentally reconcile two competing numbers every time their eye lands on the header.

  Recommended fix: Treat the plugin status as a single labeled component. Two specific options:
  - "Quantower: Disconnected" (clear label, no ambiguity, no separate "OFF" word floating).
  - When plugin is OFF, suppress the latency value entirely (or grey it out — the value is meaningless when there's nothing to ping). When plugin is ON, show "Quantower: 43ms" as a single coherent unit.
  - Unify with the status-bar `LATENCY` reading: pick one metric, display it once, label it clearly.

  Effort: Medium (touches the StatusIndicator primitive and possibly backend metric exposure).

  Screenshots: ss_5224rm25o (zoom)

### [HIGH-003] [Data] Trade Events Log: entries show entry_price 0.0 for BTCUSDT closures

  Description: On History → Trade Events Log tab, every visible `position_closed` event for BTCUSDT (278 entries total) expands to JSON like `{"symbol": "BTCUSDT", "direction": "LONG", "entry_price": 0.0, "exit_price": 110.0, "realized_pnl": 0.0, "net_pnl": -0.5, "exit_reason": "manual"}`. BTCUSDT prices in 2026 are tens of thousands. `entry_price: 0.0` and `exit_price: 110.0` are clearly wrong — these are synthetic/test/replay artifacts that have polluted the events log.

  Evidence: Screenshot ss_2916mizx9. 278 BTCUSDT entries visible across multiple timestamps, all the same shape.

  Impact: Anyone using the events log to reconstruct trade history will get nonsense data for BTCUSDT. If this log feeds downstream calculations (it might), those calculations are silently corrupted. Even if it's just display, the log is unusable for forensic analysis.

  Recommended fix: Two parts. (1) Clean up the existing pollution — likely a one-off DELETE WHERE entry_price = 0 OR symbol = 'BTCUSDT' AND entry_price < 1. (2) Add a write-time validation that rejects events with implausible entry_price (< some min for the symbol, or just != 0). (3) Add a UI filter to hide events flagged as "synthetic" or "test" if you want to keep them in the DB for debug purposes.

  Effort: Medium.

  Screenshots: ss_2916mizx9

### [HIGH-004] [Performance/Network] Dashboard polls /fragments/ws_status every ~1 second

  Description: Network monitor captured 206 requests on the Dashboard during a short observation window. ~85% were `GET /fragments/ws_status` — i.e., roughly 1 polling request per second. `GET /api/platform/connection` is interleaved every 5–6 ws_status pings (every ~5s).

  Evidence: `read_network_requests` output: requests 1–50 show the pattern; full 206-request set is in the saved tool-results file.

  Impact: 1Hz polling for what's typically a static-ish boolean (WS up/down) is wasteful. On a battery-powered laptop it adds visible CPU churn; on a server-side render it adds template-rendering load. Over 24h it's ~86k requests for a single dashboard session.

  Recommended fix: Either move WS status to SSE (push instead of pull — the engine already uses SSE per the PRD), or back off the poll rate (5s minimum, 10s comfortable), or both. The current 1s pulse should be reserved for genuinely fast-moving values (clock, latency).

  Effort: Small to medium depending on SSE integration cost.

### [MED-002] [Architecture] Row styling diverges across history tables — calibration #2 confirmed

  Description: Position History rows and Order History rows have consistent treatment.   Effort: Medium.

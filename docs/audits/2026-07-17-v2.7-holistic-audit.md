## Task-E accepted residues (both audit passes, named)

- **The `db_account_settings._resolve_db_path` write-class is not
  STRUCTURALLY closed** (both Task-E audits' top nit, rated LOW /
  per-file "defensible"). The two log resolvers of the family are
  redirect-guarded in conftest; this third (shared, transactional) one
  is not — a minimal-schema redirect `OperationalError`s on the real
  account reads its callers do (the empty-`DATA_DIR` 36-test hazard),
  and a full-data copy reintroduces cross-test accumulation. So the
  class is guarded per-test (each transactional test isolates its own
  DB/DATA_DIR) + globally by the SESSION content-hash tripwire. The one
  live-write site the tripwire surfaced (`_snapshot_and_fix_isclose` →
  `position_fill_snapshots`) is FIXED + HARD-PINNED
  (`test_snapshot_resolver_isolated_from_live_db`); a conftest
  anchor-note names the resolver. A FUTURE unisolated writer reopens the
  class → the tripwire WARNS naming the file (treat as a finding). Full
  structural closure (a non-breaking guarded copy) is a deferred
  hardening candidate, not blocking.
- **Green-run caveat (audit N2):** a green full suite proves zero live
  writes ONLY with the engine stopped AND the warnings summary read —
  the tripwire is a `UserWarning`, not a failure (deliberate: a hard
  fail would false-positive whenever the live engine runs alongside).
- **`os.makedirs(DATA_DIR/SNAPSHOTS/LOGS)` in the lifespan is not
  pytest-gated (audit N3, micro):** harmless on the operator box (dirs
  exist); on a clean checkout the suite creates empty live `data/`
  dirs — directory touch, never content. Not worth a code branch.

# v2.4 Backend Audit — 2026-05-17

## Overall Verdict

The v2.4 codebase is **operationally solid for a single-user deployment**. The
core trading loop (fill processing, position lifecycle, risk calculations) works
correctly under normal conditions. 1247 tests pass. The history page redesign
(Tasks 68-82) shipped cleanly with consistent patterns.

The primary risk areas are: (1) a logic bug in exec_link where TP/SL matching
always returns True (self-comparison), (2) data export always uses account_id=1
regardless of active account, (3) missing authentication on all API endpoints,
(4) N+1 query pattern in the fill drawer, (5) division-by-zero paths in edge
cases, and (6) WebSocket reconnect can stack overflow on persistent auth failures.
Items 1, 2, and 4 are v2.4-era regressions; the rest are pre-existing. None are
show-stoppers for current single-user operation but several affect multi-account
correctness.

Architecture is well-layered (core + adapter ring, DB mixins, pub/sub abstraction)
but shows coupling creep via 24 direct `db._conn` access points that bypass the
DatabaseManager API. Test coverage by module count is 30% (18/59 core modules have
dedicated tests), though integration coverage is higher via cross-cutting test files.

## 1. Correctness & Bug Risks

### [CRIT-002] [Correctness] core/risk_engine.py:159-161
  Description: Division by zero in slippage calculation when `best_price` is 0
  Evidence: `est_slippage = max(0.0, (est_fill_price - best_price) / best_price)` — only `entry_price <= 0` is guarded (line 147), not `best_price`
  Impact: ZeroDivisionError crashes the risk calculator mid-trade
  Recommended fix: Add guard `if best_price <= 0: return 0.0, entry_price`
  Effort: small

### [CRIT-003] [Correctness] core/order_manager.py:654-668
  Description: Division by zero risk in proportional entry fee calculation; `max()` on potentially empty list
  Evidence: `exit_time = max(f["timestamp_ms"] for f in close_fills)` — can raise ValueError if close_fills empty after filtering. Fee ratio `total_close_qty / total_open_qty` guarded by ternary but expression evaluated before selection in some Python versions.
  Impact: Crash during position close, leaving inconsistent state
  Recommended fix: Guard `max()`/`sum()` with empty-list checks; use explicit if-else instead of ternary for division
  Effort: small
  Status: VERIFIED FALSE in commit 0068a8e (Task 86) — no production change required
  Verification note (Task 86):
    Claim 1 (max() on empty close_fills): The audit cited lines 654-668 but missed the early-return guard at lines 650-652:
        if not close_fills:
            log.warning("No closing fills for %s %s — skipping", symbol, direction)
            return
    Line 659's max() is unreachable with empty close_fills. Failure-before-fix verification confirmed: removing the line-650 guard produces `ValueError: max() iterable argument is empty` at line 655 (swallowed by the outer try/except at line 737). No bug exists in current code.

    Claim 2 (ternary div-by-zero "in some Python versions"): Python ternary expressions (PEP 308, 2003) have always short-circuited by selection. The expression `a / b if b > 0 else 0.0` does not evaluate `a / b` when `b == 0`, in any Python version. Operands here are plain floats; no comparison overload or NaN trickery applies. Failure-before-fix verification confirmed: removing the ternary `if total_open_qty else 0.0` produces `ZeroDivisionError` at the division site (also swallowed by the outer try/except). The ternary IS load-bearing — but the construction is correct as written. No bug exists in current code.

    Action taken: Three regression-pin tests added in tests/test_order_manager.py::TestClosePositionGuards to protect against future removal of the line-650 guard, the prop_entry ternary (lines 665-668), and the exit_price ternary (lines 655-658). No production code modified.

## 2. Security

### [HIGH-001] [Security] main.py / api/router.py
  Description: No authentication or authorization on any API endpoint
  Evidence: No middleware, no `Depends(verify_token)`, no session validation. All routes — including account creation, trading history, and admin — are fully open.
  Impact: Any network user can access all accounts, balances, positions, and trading endpoints
  Recommended fix: Add FastAPI security middleware (JWT or session-based) before all routes
  Effort: large

### [MED-003] [Security] api/routes_orders.py:46-50, api/routes_history.py:70-75
  Description: `sort_by` and `sort_dir` parameters passed to DB layer without whitelist validation in some routes
  Evidence: Query helpers do whitelist `sort_by` against `_ALLOWED_SORT_COLS` sets — but the route handlers don't validate before passing. Defense-in-depth gap.
  Impact: SQL injection if whitelist is bypassed or new routes skip it
  Recommended fix: Validate at route level; add `sort_dir in ("ASC", "DESC")` check in routes
  Effort: small

### [MED-004] [Security] core/crypto.py:37-38
  Description: Key derivation uses plain SHA256 hash, not a proper KDF (PBKDF2/scrypt)
  Evidence: `key_bytes = hashlib.sha256(master.encode()).digest()` — no salt, no iteration count
  Impact: If master key is leaked, Fernet key derivable in microseconds
  Recommended fix: Use PBKDF2 with random salt; acceptable for current single-user deployment but should improve before multi-user
  Effort: medium

### [LOW-001] [Security] api/routes_history.py:41
  Description: Ticker input uppercased but not validated (could contain special chars)
  Evidence: `"ticker": ticker.upper()` — no format check
  Impact: Minor; parameterized queries prevent injection, but good practice to validate
  Recommended fix: Validate against `[A-Z0-9]+` pattern
  Effort: small

## 3. Performance

### [CRIT-001] [Performance] api/routes_orders.py:159-184
  Description: N+1 query pattern in position_fills endpoint
  Evidence: For each fill in the loop, 2 individual queries fire: `SELECT * FROM pre_trade_log WHERE calc_id=?` and `SELECT order_type FROM orders WHERE exchange_order_id=?`. A position with 50 fills = 100 extra queries.
  Impact: Endpoint latency scales linearly with fill count; visible delay on positions with many fills
  Recommended fix: Batch-fetch pre_trade_log and orders by calc_id/order_id lists, then join in memory
  Effort: medium

### [HIGH-003] [Performance] core/database.py (missing indexes)
  Description: No index on `pre_trade_log.calc_id` or `orders.calc_id` despite frequent lookup by calc_id
  Evidence: `SELECT * FROM pre_trade_log WHERE calc_id=?` appears 6+ times across routes_orders.py — full table scan each time
  Impact: 10-100x slower calc_id lookups as tables grow
  Recommended fix: Add `CREATE INDEX IF NOT EXISTS idx_pretrade_calc_id ON pre_trade_log (calc_id)` and same for orders
  Effort: small

### [MED-005] [Performance] core/trade_event_log.py:99+, core/calc_correlation.py:75+
  Description: Sync sqlite3 calls in modules called from async handlers
  Evidence: `conn = sqlite3.connect(db_path)` used directly; trade_events endpoint wraps in `asyncio.to_thread()` (correct) but other callers may not
  Impact: Event loop blocking for 1-5ms per call
  Recommended fix: Ensure all async call paths wrap sync DB calls in `to_thread()`
  Effort: medium

### [MED-006] [Performance] templates (HTMX polling)
  Description: 5+ HTMX elements poll at `every 30s` concurrently (including hidden tabs); 3 elements at `every 1s`
  Evidence: All tabs fire `hx-trigger="load, every 30s"` regardless of visibility
  Impact: 8+ concurrent requests per 30s cycle; 3 RPS from 1s pollers
  Recommended fix: Use HTMX `intersect` trigger or visibility API to pause hidden-tab polling
  Effort: medium

### [MED-007] [Performance] core/data_cache.py:777-789
  Description: OHLCV cache grows without hard memory bound
  Evidence: `cache.append(candle)` — soft trim at `ATR_FETCH_LIMIT + 10` but no max-age eviction or symbol cleanup
  Impact: Memory growth on long-running sessions with many symbols
  Recommended fix: Add per-symbol max-age eviction; clean up disconnected symbols
  Effort: medium

## 4. Architecture & Coupling

### [HIGH-002] [Architecture] 24 locations across codebase
  Description: Direct access to `db._conn` (private attribute) bypassing DatabaseManager API
  Evidence: `async with db._conn.execute(...)` in api/routes_orders.py (8x), core/monitoring.py (3x), core/platform_bridge.py (8x), core/reconciler.py (1x), plus others

### [MED-008] [Architecture] core/event_bus.py vs core/pubsub/bus.py
  Description: Two parallel pub/sub systems without clear usage boundary
  Evidence: `EventBus` (asyncio.Queue-based, internal) coexists with `PubSubBus` (Protocol with InProcess/Redis backends). Some modules use one, some the other.
  Impact: Confusion for contributors; risk of events not reaching all subscribers
  Recommended fix: Document when to use each; long-term consolidate onto PubSubBus

### [LOW-002] [Architecture] 40+ function-level imports across core/
  Description: Import-inside-function anti-pattern to work around circular dependencies
  Evidence: `from core.state import DEFAULT_PARAMS` inside function bodies in account_registry, data_cache, order_manager, etc.
  Impact: Hides dependencies; delays ImportError to first invocation
  Recommended fix: Restructure module boundaries to eliminate circulars; acceptable for now
  Effort: large

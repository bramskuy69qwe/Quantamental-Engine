## Findings

### [FE-CRIT-002] [Data/Architecture] Seven of eight Analytics sub-tabs return HTTP 503

  Description: Clicking Calendar PnL, Traded Pairs, MFE/MAE, R-Multiples, Risk Metrics, Funding, or Beta Exposure triggers an htmx GET to a corresponding `/fragments/analytics/*` endpoint. All seven endpoints return HTTP 503 Service Unavailable. The panels stay on a permanent "Loading..." indicator.

  Evidence: Browser console captured 7 distinct htmx errors, one per sub-tab:
  - `503 from /fragments/analytics/calendar?period=monthly&offset=0` (8:12 PM, 8:16 PM — confirmed persistent on retest)
  - `503 from /fragments/analytics/pairs?period=monthly&offset=0`
  - `503 from /fragments/analytics/excursions?period=monthly&offset=0`
  - `503 from /fragments/analytics/r_multiples?period=monthly&offset=0`
  - `503 from /fragments/analytics/var?period=monthly&offset=0`
  - `503 from /fragments/analytics/funding?period=monthly&offset=0`
  - `503 from /fragments/analytics/beta?period=monthly&offset=0`

  Screenshots: ss_6727jupq1 (Calendar PnL Loading state), ss_2049l2aha (Traded Pairs), ss_8754rp8we (MFE/MAE), ss_17647y784 (R-Multiples), ss_0499id7to (Risk Metrics), ss_84212dktp (Funding), ss_3351087t7 (Beta Exposure).

  Engine log shows a recurring `EventBus run loop error: <Queue ...> is bound to a different event loop` at high frequency around the time of the failures. May or may not be related; backend investigation needed to confirm root cause. 503 typically means a downstream dependency the route handler depends on is unavailable — could be the event bus, could be a cache, could be a deliberately-503-on-not-ready check.

  Impact: Most of the Analytics surface is non-functional. The user has no access to Calendar PnL, Traded Pairs ranking, MFE/MAE statistics, R-Multiples distribution, VaR / Risk Metrics, Funding rate analysis, or Beta Exposure. These are the analytical surfaces a trader would actually use after-hours to review performance — Analytics → Overview alone is not enough.

  Recommended fix: (1) Backend triage — establish whether the 503 is from one shared dependency (likely, given the consistent pattern) or seven separate handler bugs. The EventBus "different event loop" error in the engine log is a strong candidate for the root cause and is worth investigating first. (2) Once root cause is known, the operator should decide whether this gates v2.5 or can ship with the broken sub-tabs documented as known-down.

  Effort: Unknown without backend investigation. If it's the event-loop binding issue, likely small (asyncio.Queue creation order in startup). If it's seven separate broken handlers, larger.

### [FE-HIGH-007] [UX] Analytics "Loading..." state never clears on htmx 5xx — Task 108 fix is incomplete

  Description: Audit-01's CRIT-001 (`/fragments/account-detail/1` returned 500 silently) was marked resolved via Task 108, which the audit-01 follow-up indicated added an htmx error handler. In Audit-02, all seven broken Analytics sub-tabs do log an error to the browser console (so the handler IS firing). But the visible "Loading..." text in the panel body never clears or transitions to an error state. The user sees a spinner forever.

  Evidence: All seven sub-tabs show identical "Loading..." text (screenshots above) even after several seconds and console-confirmed 503 responses. No toast, no error banner, no inline error message replacing the loading state.

  Impact: The htmx error handler logs but does not communicate. A non-developer using the engine has no signal that anything failed — they'd reasonably assume the data is just slow and wait, then give up, with no useful guidance. This is worse than the original silent-500 failure because there's now an "in progress" affordance ("Loading...") that's lying about the state.

  Recommended fix: Extend the htmx error handler to replace the target element's content with a visible error state. Two patterns work:
  - **Inline replacement**: swap the loading text for an "Failed to load (HTTP {status}) · Retry" inline element.
  - **Toast + grayed panel**: keep panel but gray it out and show a dismissable toast with the error.
  Choose whichever fits your design language. The key is: the loading text must go away, and the user must see *something* indicating failure.

  Effort: Small (one global htmx hook).

### [FE-MED-017] [Architecture] Period selector duplication on Analytics → Equity Curve

  Description: Two distinct period selectors with different option sets are visible on Equity Curve:
  - **Page-level header** (visible across all Analytics sub-tabs): `< May 2026 >`, then `Month / Week / Quarter / Year / 30D / 90D / All`.
  - **Equity Curve panel header** (inside the chart card): `1W / 2W / 1M / 3M / 6M / 1Y / All`, plus separate "Log scale" and "Drawdown %" checkboxes.

  The two control sets share semantic intent (pick a time range) but offer different options. Their interaction is undocumented: does the chart-level selector override the page-level? Does selecting "1Y" in the chart panel sync the page header? Neither is obvious.

  Evidence: Screenshot ss_5579nji3m (Equity Curve sub-tab with both selectors visible at top).

  Impact: This is the same architectural pattern flagged in audit-01's MED-007 (Regime page period selector duplication) — every page with both page-level and per-panel periods has the same precedence ambiguity. Continued evidence of the missing PeriodSelector primitive.

  Recommended fix: Build the PeriodSelector primitive proposed in audit-01's recommendations. For Equity Curve specifically: decide whether the chart panel needs its own period selector (it adds zoom granularity not in the page-level options, so probably yes), and document the precedence — either page-level filters the data set, chart-level zooms within it; or chart-level overrides and the page-level becomes inactive while overridden. Show "(custom)" or similar to signal override state.

  Effort: Medium (primitive + page-by-page migration).

### [FE-LOW-008] [Data] Equity Curve panel: "Range" value doesn't match high-minus-low

  Description: Equity Curve panel header shows the day-summary line `O $89.30 · H $100.72 · L $79.77 · C $80.50 · Chg +$0.20 (+0.25%) · Range $100.95 (126.55%) · CF +$0.00 · Adj Chg +$0.20 (+0.25%)`.

  H − L = $100.72 − $79.77 = $20.95, but Range shows $100.95. Off by an order of magnitude. The percentage (126.55%) also seems implausible for the data range shown on chart.

  Either Range is measuring something other than H − L (in which case the label is wrong), or there's a calculation/display bug.

  Evidence: Screenshot ss_5579nji3m.

  Impact: Number visible on a trader's performance dashboard that doesn't match the obvious arithmetic. At best confusing, at worst misleading.

  Recommended fix: Identify what Range is supposed to measure (lifetime drawdown? range from initial equity? something else?), then either fix the calc or fix the label.

  Effort: Small (calc / label fix).

## Cross-cutting observations

**The 503 pattern is uniform across all 7 broken sub-tabs.** Same status code, same "Loading..." persistence, same error log shape in browser console. This strongly suggests a single shared dependency is failing rather than seven independent handler bugs. The EventBus event-loop binding error in the engine log is the most plausible candidate — if the analytics handlers all wait on the event bus to publish their query intents (or subscribe to a downstream computation), and the bus is broken, every handler 503s. Worth backend triage as a high-priority single issue.

**A new empty/transitional state pattern is now visible.** Audit-01 cataloged 7 distinct empty-state treatments under MED-006. Audit-02 surfaces an 8th: the "Loading..." text shown while htmx awaits a fragment. It's not designed; it's just a static fallback the htmx target element rendered before the swap. The eventual loaded state, the error state (currently silently broken — see FE-HIGH-007), and the empty-but-loaded state are all different design problems that the missing EmptyState primitive ought to handle together.

**Equity Curve appears to share the chart component with Dashboard's equity curve.** Same auto-scale-to-headroom problem (y-axis tops at $180 for a curve clustered $80–$100). Same control surface (toggles for log scale and drawdown %). If they're literally the same component, fixing FE-MED-009 in one place fixes both surfaces. If they're separate copies, that itself is a refactor candidate.

**Coverage of 7 sub-tabs was not possible.** The audit prompt's request for visual / data-quality / number-formatting / empty-state observations across all 8 sub-tabs cannot be fulfilled while the 503s persist. Once those are fixed, a re-audit pass on the 7 currently-broken sub-tabs would surface a substantial second wave of findings (probably 10–20 — based on the depth audit-01 found on Overview alone, which had its data intact).

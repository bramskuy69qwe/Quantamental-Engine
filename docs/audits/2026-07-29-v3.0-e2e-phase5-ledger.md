## E2E-P5-001 — CRIT — user-data WS died at boot with no retry; fill pipeline silently dead for 2 days

**Fixed in `7e6cf62`.** Full mechanism in the commit body; the short chain:
sticky adapter priority left at `background` by boot backfills → `create_listen_key`
inherited it → weight tracker shed the call at 114% → `_startup_fetch` logged and
moved on (no retry) → user-data socket (the SOLE fill source) dead until manual
restart → fills arrived only via REST reconcile (`source='binance_rest'`, no tpid,
no close-row build) → **zero `closed_positions` after 2026-07-26 22:08** across two
days of live trading. `monitoring` said `WS stale for 9999s` throughout; no UI
surface (the FEED dot tracks the MARKET socket, which was healthy).

**Fix (3 parts + 8 pins)**: explicit `priority="urgent"` on listen-key
create/keepalive · `finally`-restore at all three background-priority sites ·
`_ws_startup_retry_loop` (backoff 15/30/60/120 s, stop+start per attempt, exits on
connected, own correlation tick).

**Live verification — engine restarted 2026-07-29 01:55 (STRONG PASS, one caveat)**:

| Signal | Failed boot (07-28) | After the fix (07-29) |
|---|---|---|
| `created WS adapter` | 21:20:07 | 01:55:16 |
| `WS startup failed: Weight budget exceeded` | 21:20:43 (+36 s) | **absent** (>3 min elapsed) |
| `WS RETRY n FAILED` | n/a | absent — the retry loop was never needed |

The boot burst still saturates the budget (`recover_offline_trades` and OHLCV both
logged 95 % rejections at 01:55:29) — i.e. the SAME pressure that shed the listen
key on 07-28 — and the listen key nonetheless bound. That is the fix doing exactly
its job. **Conclusive proof waits on the first live fill** carrying
`source='binance_ws'` (operator was flat at verification time); Phase 6's trade
scenarios produce it by construction.

**P5-R2 confirmed empirically while verifying**: NO HTTP door exposes the user-data
socket's state. `/api/state.exchange_ws` is the MARKET socket; `/api/system` carries
cadences only; the `ws_status` log ring had rotated past the connect line. The
engine's primary fill source cannot be checked from outside the process — which is
why a two-day outage went unnoticed.

## Filed residuals (scoped follow-ups, not fixed here)

- **P5-R1 (HIGH candidate)**: the REST reconcile fill path inserts fills but never
  schedules the close-row build — it silently became the de-facto fill source when
  the WS died. Either it should schedule builds, or its use as sole source should
  alarm loudly.
- **P5-R2 (MED)**: no UI surface for user-data-socket death. The chrome FEED dot is
  the MARKET socket; `ws_status.connected` (user-data) is invisible in v3. An
  operator traded for two days with no fill pipeline and nothing on screen said so.
- **P5-R3 (LOW)**: `monitoring`'s `WS stale` alert fires forever with no escalation
  and no action; consider wiring it to the new retry loop's health.
- **P5-R4 (MED, NEW — exposed by the backfill)**: `rebuild_closed_positions.py`
  writes `mfe=0.0 / mae=0.0` on rebuilt rows pending reconciliation, not NULL.
  The v3 truthfulness rule is "both null → `—`, never a zero bar" (a `||0`
  coercion fabricates certainty). So a rebuilt-but-unreconciled row renders a
  MEASURED-AT-ZERO excursion instead of "not measured". Live right now: all 26
  recovered rows show `0.0/0.0` because the reconciler is rate-limited (see
  below). Fix shape: write NULL and let the reconciler fill it.
- **Reconciler drain is throttled, not stuck**: at 01:55 it processed 2 SNDK rows
  then logged `aborting — rate limited`; the 900 s sweep retries. Queue 27 → will
  drain over the next hours. Excursion bars populate as it goes.
- **OBS-001 update**: the weight-tracker pressure (94–95% throttling) observed just
  before the first silent engine stop is consistent with the same boot-burst
  pressure that shed the listen key. Stops themselves remain unexplained.

## E2E-P5-002 — MED — the countdown chip reported LINKABLE for CANCELLED calcs

**Fixed in `b2b9436`.** Found by the first live-mutation run: after a successful
cancel through the Linkage dialog (server "Calc cancelled.", Active Calcs → 0),
`GET /calculator/link-window-status/{id}` still answered
`{"status":"LINKABLE","remaining_s":21498}`. The route special-cased only
`matched`/`linked` → LINKED; every other status fell through to the raw
time-window countdown — but the matcher's candidate set is
`status IN ('active','released')` (`calc_correlation.py:389`), so a cancelled /
superseded / expired / completed calc can NEVER link. The chip advertised a green
`✓ LINKABLE` for a dead plan, contradicting the cancel dialog's own warning that a
later fill "lands UNPLANNED unless a fresh calc is run".

Fix: terminal non-linkable statuses return `EXPIRED` (existing terminal bucket —
stops the poller, and its copy is the right instruction). One status read per poll
preserved. Pins: `tests/test_link_window_terminal_status.py` (8), including a pin
on the matcher's candidate set as the CONTRACT behind the mapping.

**Live-verified** in run `5-20260729-0726`: `postCancelStatus: EXPIRED`.

## P5-R5 (MED, NEW) — post-restart weight saturation makes Pre-Trade unusable

Observed in run `5-20260729-0725` (≈1 min after an engine restart): every
Pre-Trade pane rendered `Data fetch error: Weight budget exceeded (95%,
priority=normal)`, `/api/price/{ticker}` returned no price, and Calculate
correctly refused to size (MARKET mode requires a live price). Recovered on its
own within minutes. The UI is TRUTHFUL throughout — but the operator cannot size a
position for the first minutes after every restart, which is exactly when they are
most likely to want one. Same root pressure as E2E-P5-001 (boot burst vs weight
budget), second symptom. Fix shapes to consider: stagger/defer the boot backfills,
or raise the price poll's priority tier.
Harness follow-up applied: the spec now polls the price door for readiness instead
of a fixed wait.

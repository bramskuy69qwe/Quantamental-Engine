## E2E-P6-001 — HIGH — order-form TP/SL never linked (algo path skipped parent re-enrich)

**Fixed in `e48ce0b`; live-verified twice.** Full mechanism in the commit body.
Short version: Binance conditional orders are invisible to the user-data WS, so
the engine learns order-form TP/SL only through the 15 s REST algo sweep — which
lands AFTER a filled market order's last WS update. Nothing re-ran the entry's
enrichment, so `tp/sl_trigger_price` stayed NULL forever, `_try_correlate`
hard-returned, and **auto-link could never work on the operator's normal bracket
workflow** — silently: no error, no warning, no UI signal beyond a chip that
never turns green. `process_order_update` had carried
`_re_enrich_parent_on_child_arrival` for precisely this case since 2026-06-08;
it was never wired into the algo path.

**Verification 1 (the ETHUSDT position that exposed it, after restart)**:
`tp_trigger_price NULL → 1970.0`, `sl_trigger_price NULL → 1860.0`,
`link_status NULL → UNPLANNED` (matcher RAN; UNPLANNED correct on the merits —
both calcs were expired/superseded by evaluation time).

## ★ Harness false finding — corrected record (calibration)

The `calc-row-absent` oracle matched **any** Active-Calcs row for the ticker, so
when a SECOND SOLUSDT calc appeared 27 s later (id 177 — ordinary operator
re-calc behaviour; 24 of the last 60 calcs are same-ticker re-calcs within 120 s)
it reported our calc as still present. **Our calc had correctly gone to
`matched` and left the pane.** The operator was asked to rule on mislabeled
evidence and understandably marked it a confirmed finding.

Fixes: the oracle is now **calc-scoped** — it asserts identity via
`/api/linkage/calcs` `calc_id`, never ticker text. Discipline reaffirmed: an
oracle that cannot distinguish OUR artifact from a similar one manufactures
findings, and an operator verdict is only as good as the evidence handed to them.

## P6-H1 — budget calibration (harness, not a defect)

The lifecycle map's 10 s `chip-linked` budget assumed WS-visible protective legs.
The **order-form** path adds a hop: fill → algo sweep (≤15 s) → parent re-enrich
→ matcher → chip poll (≤5 s). Honest bound ≈ 30 s; raised to 40 s. This is a
genuine property of the bracket workflow, now documented in the scenario data.

## E2E-P6-002 — HIGH — manual-link candidates were EMPTY for every MARKET order

**Symptom (L2)**: the near-miss entry was classified perfectly —
`link_status = NEEDS_MANUAL_REVIEW`, audit shows 4/6 (ticker ✓ direction ✓
window ✓ entry ✓ · tp 72.4 vs 72.41 ✗ · sl 74.5 vs 74.51 ✗) — the strip appeared
in the inbox, and then the resolver said **"No candidate calcs in window"**. The
operator could only mark UNPLANNED. The manual-link RECOVERY path — the whole
point of the inbox — was unusable.

**Mechanism (investigated)**: `find_candidate_calcs`, the LOOSE finder behind the
resolver, read `order["price"]` only and returned `[]` at its
`if not ticker or not entry_price` guard. A Binance MARKET order has
`price = 0`; its executed entry is `avg_fill_price`. The STRICT matcher already
knows this (`order_enrichment.py:325-353` passes both and compares the fill for
market orders) — the loose finder never did. Worse, `list_needs_review` did not
even SELECT `avg_fill_price`, so the value was absent from the payload the finder
receives AND from what the UI can render (the strip shows `MARKET @ 0.000000`).

So: **auto-link works for market orders, manual link never could.** The two paths
disagreed about what a market order's entry price is.

**Fix**: `entry_price = price or avg_fill_price` in the finder (price-first, so
limit orders are unchanged), and `list_needs_review` now carries the column.
Pins: `tests/test_manual_link_market_candidates.py` (6), including a guard that
the finder keeps its explicit `db_path=config.DB_PATH` (the Phase-4 near-miss).

## Harness corrections (mine, not the engine's)

- **A1's "confirmed finding" was a timing artifact.** The audit proves the
  position linked 6/6 to calc `094e58ae`; A2's very next assertion saw
  `S LINKED OFF-PLAN`. My assertion simply ran before the order-form hop

  adjudicate a miss my budgets manufactured.
- **X1's oracle was too weak to prove its own claim**: `closed-row-present`
  counts recent rows for the ticker, so it reported "3 recent rows" both before
  and after the second close. The scenario passed, but the DB — not the oracle —
  is what actually proved one-row-per-closing-order. Needs a delta assertion.

## Findings

### [FE-HIGH-009] [UX/Data] Countdown widget shows `✗ PLAN EXPIRED` on freshly-submitted ELIGIBLE calc

  Description: After submitting an eligible calc on the Calculator page, two parts of the right-side result panel show contradictory state:

  - Top banner of the result panel: `✗ PLAN EXPIRED — recalculate to link new fills` (red, terminal state)
  - Just below it, CALCULATED POSITION: `ELIGIBLE` (green badge)

  Reproduced on multiple submissions during the session. Reproduced both immediately after submission AND ~8 seconds after submission (one full poll cycle past). Banner doesn't update to LINKABLE.

  Steps to reproduce (confirmed):
  1. Navigate to /calculator with form pre-populated (TICKER, TP, SL, account default link window).
  2. Click Calculate. Wait for response (occasional 422 — see FE-MED-027 below).
  3. Observe: top banner reads `✗ PLAN EXPIRED`, CALCULATED POSITION reads `ELIGIBLE`. Two states on one panel.

  Possible root causes (need backend dive to confirm):
  - Countdown widget rendering with a stale `calc_id` from a previous calc on the page. When a new calc is submitted, the htmx swap updates the calculated-position card but not the countdown widget's `calc_id` reference (different swap targets / hx-include scope).
  - Widget's poll-status endpoint returns EXPIRED for the new calc_id (a backend issue — maybe a race where the calc is inserted but the link-window window calculation reads timestamp from a different source).
  - Widget renders with previous calc's calc_id and never re-resolves on subsequent submissions until full page reload.

  Evidence: Screenshots ss_6893mt6em (eligible BNB calc, banner says PLAN EXPIRED), ss_7078h1tr4 (re-submit confirms same state), ss_6259nnfgg (8-second wait, no update).

  Impact: Critical UX bug for the link-window feature. The whole point of v2.4.1's HIGH-027 work was to give traders a clear signal that fills within 6h of the calc get auto-linked. If the countdown UI says EXPIRED for a fresh calc, the trader gets exactly the wrong message — they'd think their plan is already stale and either skip the trade or assume the auto-link won't work.

  Recommended fix: Backend triage first — log the calc_id the widget polls vs. the calc_id from the most-recent calc submission, and confirm whether they match. If they match and EXPIRED is being returned legitimately, the bug is in the time-window computation. If they don't match, the bug is in how the widget's swap target updates on calc submission.

  Effort: Small to investigate; small-to-medium to fix once root cause is known.

### [FE-MED-027] [UX/Data] First Calculate POST after page load returns 422

  Description: Click sequence to reproduce:
  1. Navigate to `/calculator` (form has persisted state from prior session — TICKER=BNBUSDT, TP=680, SL=620 in this case).
  2. Click Calculate.
  3. **Result: HTTP 422.** Red toast top-right reads `Request failed: 422 /calculator/calculate`. Right-side panel shows "Couldn't load this section." with a Retry button.
  4. Click Calculate again (without changing anything).
  5. **Result: HTTP 200.** Calc submits successfully, populated result renders.

  Reproduced twice during this session: once on BTCUSDT (first submission), once on BNBUSDT (after page refresh).

  Evidence: Screenshots ss_0731m1m72 (first 422 with red toast), ss_6311dbjzx (second 422 reproduction), ss_7078h1tr4 (subsequent retry succeeded).

  Network observations: 14 of 14 `/calculator/calculate` POSTs in the audit's network log returned 200; the 422s happened earlier before network tracking was active. Confirmed via browser console error log instead.

  Impact: User has to click Calculate twice on every fresh page load. Unintuitive. And the toast surfaces raw HTTP details (`Request failed: 422 /calculator/calculate`) — developer-format error message that doesn't tell the user what's actually wrong or what to do.

  Recommended fix: Two parts:
  - **Backend**: figure out why the first POST validates incorrectly. Possible culprits: form serialization timing (the live entry price hasn't settled before the form submits), missing `hx-include` for some field, or a validation that depends on a price refresh that races with the submit.
  - **Frontend (toast)**: replace raw HTTP error string with user-friendly text like "Submission failed validation. Please check entry/TP/SL and try again." Same family as Session B FE-HIGH-008's `'RegimeFetcher' object has no attribute 'close'` toast surfacing raw exception strings.

  Effort: Small (toast wording) to medium (backend race investigation).

### [FE-MED-028] [UX] Calculator countdown widget tracks "last submitted calc on this page" — not "currently-displayed form values"

  Description: When the user types a new ticker into the Calculator form (without clicking Calculate), the right column updates via `/calculator/refresh/{TICKER}` to show live BNB/BTC/etc. preview values. But the countdown widget at the top of the right column still tracks the LAST SUBMITTED calc — not the new ticker the user is now editing.

  Reproduction:
  1. Submit a BTCUSDT calc. Countdown shows whatever state the BTC calc is in.
  2. Type "BNBUSDT" into TICKER field, Tab out (triggers refresh).
  3. Right-column preview values update to BNB. But countdown banner at top is still the BTCUSDT calc's countdown.

  Specifically observed: After changing ticker from BTCUSDT to BNBUSDT, countdown banner read `✗ PLAN EXPIRED` even though only ~30 seconds had elapsed since the BTC calc was submitted. The "expiration" was probably triggered by the ticker change invalidating the BTC plan (because the form context changed), not by actual time elapse.

  Evidence: Screenshot ss_4782sznes (ticker changed to BNB, BNB preview values populated, but countdown still says PLAN EXPIRED — and the BTC calc was only ~30s old at that point).

  Impact: Widget gives misleading time-pressure feedback. A user editing the form to refine an idea would see their pre-edit plan as expired even if it's seconds old. Decoupled from actual mechanics.

  Recommended fix: Decide on widget semantic — is it tracking (a) "the calc you just submitted" or (b) "the calc represented by the current form values"? Option (a) is simpler but should hide when form has drifted from the submitted calc. Option (b) requires re-resolving the widget after every refresh. Probably (a) with a "form drifted" hint when the user has typed something the calc doesn't reflect anymore.

  Effort: Medium (semantic decision + implementation).

### [FE-LOW-022] [UI] Calculator SETUP SUMMARY size precision differs from CALCULATED POSITION

  Description: For the same eligible BNBUSDT calc, two parts of the result panel show the same size with different precision:
  - **CALCULATED POSITION → SIZE (CONTRACTS)**: `0.0314` (4 decimals)
  - **SETUP SUMMARY → SIZE (CONTRACTS)**: `0.031400` (6 decimals)

  Same underlying value, two formatters.

  Evidence: Screenshot ss_2612yxvc3.

  Impact: Cosmetic. Same family as Session A' FE-MED-019 (uniform 4-decimal precision on MFE/MAE) — number formatting needs centralization.

  Recommended fix: Single `format_contracts(symbol, value)` helper used in both places. Pick one precision — 4 decimals matches most other engine displays; 6 decimals matches Binance contract sizing for some pairs. Decide based on minimum tick size for the symbol.

  Effort: Trivial.

### [FE-LOW-024] [Data] Calculator percentage values display 5-decimal precision for invalid TP/SL

  Description: When TP/SL are off-scale for the current symbol (e.g., TP=80000 when current BNB price is 644), the percent display gets absurd:
  - `TP: 12314.75%` and `SL: 11694.81%`

  These are mathematically correct but uselessly imprecise — 5 significant digits when the data is clearly garbage. A clamp or sanity check at the display layer would avoid the visual noise.

  Evidence: Screenshot ss_4782sznes (ticker changed to BNB, TP=80000 still in form, %s blow up).

  Impact: Cosmetic; happens only during ticker-change transitions before user updates TP/SL.

  Recommended fix: When abs(percent) > 100%, display as `>100%` or trigger an inline warning ("TP/SL out of range for current price — update before calculating"). Or auto-clear TP/SL when ticker changes (already might be done — couldn't verify the auto-clear behavior with the 422 issue intercepting).

  Effort: Trivial.

Then in browser: navigate to `http://localhost:8000/calculator/link-window-status/<calc_id>`. Should render LINKED_CONFIRMED (green) regardless of elapsed time. Note polling — should also stop.

### Test EXPIRING_SOON state visually (via UI; no SQL needed)


Then submit a fresh BNB calc on /calculator. After ~1 minute (when remaining < 300s), the countdown should transition from LINKABLE → EXPIRING_SOON (amber). Continue watching past ~6 min for the EXPIRED transition.

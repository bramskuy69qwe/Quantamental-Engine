You are designing **one tab** — the **Models** tab (a.k.a. Model Library) — for the v3.0 redesign of
**Quantamental Engine**, a single-operator, localhost **desktop trading cockpit** for futures/crypto.
The operator places trades on exchanges (Binance, etc.); the engine *observes* the fills, sizes risk,
links orders to plans, and tracks performance. It is a power-user tool: dark, data-dense, used on a
wide desktop monitor. v3.0 is a ground-up visual refresh; this brief is just the Models surface.

A minimal functional version of this tab is already being built in the current stack — your job is the
**polished v3.0 design** it will be rebuilt against. Design for real data, real workflows.

## The core entity: a "Model"
A reusable, **exchange-agnostic** trading model the operator stores once and uses everywhere. Each has:
- **Identity** — name, type (`Macro` / `Micro` / `Both`), description.
- **Risk & sizing preset** — risk % per trade, sizing rule, match window (seconds), TP methodology,
  SL methodology, "apply regime multiplier" toggle, default size override.
- **Strategy definition** — freeform notes + a structured config (entry logic, exit logic, target
  universe, regime config).
- **Imported backtest runs (1 model → many runs)** — performance imported from 3rd-party backtesting
  apps (MultiCharts first; more later). Each run = summary stats + a trade-by-trade list + an equity
  curve. **The engine does NOT run backtests itself** — performance always arrives via file import.

## What the operator does here (jobs-to-be-done)
1. Browse / search / filter the library of models.
2. Create, edit, delete a model.
3. Import a backtest report (**file upload**, MultiCharts `.xlsx`/`.xml`) and attach it to a model;
   preview the parsed summary before confirming.
4. Review a model's performance — compare runs, read summary KPIs, scan trades, view equity/drawdown.
5. **"Load into Calculator"** — push a model's risk preset into the live risk calculator for a symbol.
6. See **where a model has been used** (attribution: which live/closed positions came from this model).

## Screens & states to design
- **A. Library (list)** — all models. Show name, type badge, headline KPIs from the latest/best run
  (Net P/L, Win %, Profit Factor, Max Drawdown, # Trades), last-updated. Search + filter by type +
  sort. "+ New Model". Include the **empty state** (no models yet).
- **B. Model detail** — header (name / type / description + actions: Edit · Load into Calculator ·
  Delete) and sections: Risk & sizing preset · Strategy definition · Backtest runs (list of imported
  runs → open one) · Usage/attribution (positions & plans tagged with this model). Include the
  **"no backtests imported yet"** state with a prominent Import action.
- **C. Backtest run report** — the rich performance view for one run:
  - **KPI header** — Net Profit, Gross Profit/Loss, Profit Factor, Win %, Total Trades,
    Max Drawdown (**both $ and %**), Sharpe, Avg Win / Avg Loss, Largest Win/Loss, Max consecutive
    win/loss.
  - **Equity curve** chart (cumulative equity over the trade sequence) with a **drawdown** overlay or
    underlay.
  - **Trade list** table: #, side (long/short), signal, entry & exit datetime, entry & exit price,
    contracts, P/L ($ and %), cumulative P/L, run-up, drawdown, exit reason (TP / SL / manual).
    Sortable, filterable (long/short, win/loss), virtualized/paginated (hundreds of rows).
  - Optional extras: P/L distribution, MAE/MFE, periodical breakdown (hourly/daily/monthly).
- **D. Create / edit model form** — metadata + risk-preset fields + strategy text. Inline validation.
- **E. Import backtest flow** — choose source app (MultiCharts) → upload file → **parsed-summary
  preview** → confirm. Include the **parse-error / unrecognized-file** state.

### Real data shapes to honor (from an actual MultiCharts report)
- **Summary KPIs:** Net Profit, Gross Profit, Gross Loss, Profit Factor, % Profitable, Total # Trades,
  Max Strategy Drawdown ($ + %), Sharpe, Avg Win, Avg Loss, Largest Win/Loss, Max consec. win/loss.
- **Trades:** trade # · type (Entry/Exit Long/Short) · signal · entry & exit datetime · price ·
  contracts · Profit ($ and %) · Cum. Profit · Run-up · Drawdown · exit reason.
- **Equity curve:** cumulative P/L over the trade sequence (+ initial capital) with per-trade drawdown.

## Visual & UX direction
- **Dark theme**, professional trading-cockpit aesthetic — "Bloomberg-meets-clean-SaaS." High
  information density without clutter; strong typographic hierarchy; **tabular numerals** for money/%;
  semantic color (green profit / red loss) with a colorblind-safe variant.
- **Desktop-first** (wide monitor); degrade gracefully to laptop width. Not mobile-priority.
- Fast scanning: KPI cards, sortable tables, sticky headers, badges for model type + link/attribution
  status, clean financial charts.
- **Accessibility:** sufficient contrast, visible focus states, keyboard navigation for tables/forms.

## Constraints (so the design is buildable)
- It will be implemented in a **server-rendered** web stack (FastAPI + Jinja + HTMX today; v3 may add
  richer client interactivity). Favor layouts that work as server-rendered fragments with progressive
  enhancement; don't assume a heavy SPA framework.
- **Single operator, localhost** — no auth/login, no multi-user/team UI.
- Models are **exchange-agnostic** (no per-exchange variants inside a model).
- Make the **import** path and the **"no backtests yet"** states first-class — performance only ever
  comes from imported reports.
- Produce **reusable components** (KPI card, model card, type/status badge, equity chart, trade table,
  file-upload, form fields) so the rest of v3.0 can share them.

## Deliverables
1. High-fidelity mockups for screens **A–E**, including empty / loading / error states.
2. A **reusable component inventory** (the primitives above) for the broader v3.0 system.
3. Responsive notes (wide desktop → laptop).
4. Interaction annotations (hover, sort, filter, "Load into Calculator", import preview → confirm).
5. Primarily dark mode; note any light-mode considerations.

## Creative latitude
Where the data is sparse, propose smart defaults. Feel free to introduce: side-by-side **comparison of
multiple backtest runs**, tags/collections for organizing models, a model "performance at a glance"
sparkline on the library cards, and a clean attribution/usage timeline. Surprise me — but keep it
buildable and cohesive with the rest of v3.0.

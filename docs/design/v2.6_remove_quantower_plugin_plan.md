# v2.6 — Remove Quantower Plugin Integration (Implementation Plan)

**Status:** design — pending execution.
**Created:** 2026-06-24
**Branch:** dedicated `v2.6/remove-quantower-plugin` off the current release HEAD.
**Scope:** delete the Quantower live-ingestion path, its UI, its auth surface, and the C#
plugin project — so the engine reads only from exchanges. The v3 UI rewrite is out of scope.

---

## 1. Context

The engine has two data-source modes today:

- **exchange-WS** — Binance/Bybit/MEXC adapters. The primary, always-on data path since v2.5.
- **Quantower plugin (optional)** — a C# strategy that pushes fills/positions/orders to the
  engine over `/ws/platform` (REST fallback `/api/platform/*`). Marked deprecated in Task 150
  (2026-05-19) with an archive target of 2026-06-16 (now passed). Dormant in the default
  "standalone" mode.

Removing it is a simplification: it deletes a dormant second ingestion path, its shared-secret
auth (`PLATFORM_TOKEN`), its UI (platform selector + connection banner + polling), and the C#
plugin project. The matcher, WS manager, and order/fill/position pipeline are all 100%
exchange-driven and need no Quantower data.

**Guiding principle:** removing the **live ingestion path** is *not* the same as removing
**recognition of the historical `'quantower'` source value**. Old DB rows
(`source='quantower'` fills, `qt:`-prefixed `trade_key`s) are kept as-is (operator decision);
only the live WS/REST intake, UI, and config are removed. Anything that *reads / displays /
dedups* those historical rows must keep working.

---

## 2. ⚠ CRITICAL FINDING — this is *extract-then-delete*, not a straight delete

The "zero Quantower coupling, safe to delete" read is **semantically true but structurally
false**. `core/platform_bridge.py` constructs the engine's **only** production `OrderManager`,
and the entire exchange-WS order/fill pipeline reaches it *through the `platform_bridge`
singleton*. Deleting the bridge first would break exchange-only trading. The bridge must first
be **emptied of its load-bearing role** (extract `OrderManager`, constant-fold
`is_connected → False`), and only *then* deleted.

### Verified coupling inventory (HEAD `1fe4178`; line numbers may drift)

- `db` imported at `core/platform_bridge.py:56`; `order_manager` property at `:195`;
  `is_connected` property at `:199` (`len(self._ws_clients) > 0`).
- All other `OrderManager(...)` matches are in `tests/`.

**`platform_bridge.order_manager` reads (Phase 1 — repoint to the new singleton):**
- `api/routes_dashboard.py:67, 123, 141` — `.open_orders`
- `api/routes_history.py:128` — `.open_orders` (late import at `:121`)
- `core/exchange.py:313` — `.enrich_positions_tpsl(...)` (late import at `:311`)
- `core/schedulers.py:222, 481, 498, 709, 724, 776, 850` — `process_order_snapshot`,
  `refresh_cache`, `process_algo_snapshot`, `_position_primary_calc` (top import at `:30`)
- `core/ws_manager.py:275, 280, 357, 362` — `detect_and_persist_amendment`,
  `process_order_update` (late imports at `:246`, `:330`)

**`platform_bridge.is_connected` reads (Phase 2 — constant-fold to `False`):**
- `core/exchange.py:320`, `core/exchange_income.py:267`,
  `core/exchange_market.py:33, 142`, `core/monitoring.py:366`,

**No circular-import risk for the extraction:** `core/order_manager.py`, `core/db_orders.py`,
and `core/db_exchange.py` reference `platform_bridge` only in **comments/docstrings**, never as
runtime imports. So a new singleton importing `core.database` + `core.order_manager` is safe,
and `platform_bridge` can consume it without a cycle.

### Landmines — keep these (do NOT remove)
- **L1 — OrderManager host:** extract before delete (Phase 1). There must remain exactly **one**
  `OrderManager` instance process-wide (it holds in-memory `open_orders` /
  `_position_primary_calc` state); the bridge must consume the shared singleton, not build a
  second one.
- **L2 — `resolve_tpsl_direction`** (`core/order_state.py`) sits *between* the two QT maps but is
  used by `exchange.py`, `order_manager.py`, `ws_manager.py`, `tests/test_om5_tpsl_matching.py`.
  Delete only `QT_STATUS_MAP` + `QT_ORDER_TYPE_MAP`; keep `resolve_tpsl_direction` verbatim.
- **L3 — `UpdateSource.PLATFORM`** + `apply_account_update_platform` (`core/data_cache.py`) are
  referenced by ~6 correlation-log tests and the position/account conflict-resolution logic.
  Keep the enum member as a now-unused-but-tolerated value; deleting it is pure churn + a wide
  test rewrite on a localhost app.
- **L4 — historical rows kept as-is** (operator decision). `source='quantower'` fills and `qt:`
  `trade_key`s stay. Keep `scripts/dedup_fills.py` `SOURCE_PRIORITY["quantower"]=0` (removing it
  re-ranks historical quantower fills and changes dedup keep/delete decisions); leave
  `tests/test_an2_quantower_cleanup.py` + `core/migrations/000_split_databases.py` untouched.
- **L5 — `/api/backtest/qt-import`** (`api/routes_backtest.py`) writes `{"source":"quantower"}`
  into the *generic* `backtest_sessions` table (not the plugin). Leave in v2.6; retire in v2.7
  once the model-library upload framework supersedes it.

## 3. Phasing rationale

Phases are ordered so the bridge is **emptied before it is deleted**, and every phase leaves the
engine **bootable + suite-green** (so each can ship/commit independently). Critical path is
**Phase 1 → 2 → 5** (extract → de-branch → delete); Phases 3, 4, 6 are cleanup that can land in
any order after Phase 2.

```
Phase 1: Extract OrderManager (bridge no longer load-bearing)
  └─> Phase 2: Constant-fold is_connected → False (standalone-only)
        ├─> Phase 3: Collapse active_platform setting
        ├─> Phase 4: Templates / config / order_state / dedup
        └─> Phase 5: Archive + delete bridge / routes / C# plugin
              └─> Phase 6: Tests (repoint mocks) + docs
```

Effort tiers: **S** (≤1 day), **M** (2–4 days). All phases here are S–M.

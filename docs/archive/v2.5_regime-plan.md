# Regime Plan — JSON Classifier, External Backtest, ML-Ready Interface

## Direction

**Supersedes the v2.5–v2.7 in-engine backtester roadmap.** The engine is
**storage + analytics + forward-cadence pacing** — not a strategy
backtester.

- Strategy backtesting happens externally: **MultiCharts first**,
  vectorbt / backtrader converters added later.
- The regime classifier **runs live in the engine** for position sizing.
- The engine **keeps a lightweight regime-validation capability** (not a
  strategy backtester): counterfactual re-sizing of real trades + forward
  two-track tracking. This is what answers "does regime sizing actually
  help?"
- ML is an **end-phase** item — implementation #2 behind a stable
  interface, built only after rule-based regime sizing has been
  validated. The seam keeps the rule → ML swap cheap (so ML is closer
  than the original v2.7 horizon), but it is *not* near-term-now.

## What this supersedes / drops

**Dropped** (was in the old v2.5–v2.7 roadmap):
- In-engine offensive / integration **strategy** backtest adapters.
- Native strategy backtester, in-engine walk-forward strategy retrain.
- The 6 audit-02 backtest-scope findings (parked
  `BLOCKED-ON-OPERATOR-DECISION`) → **SCOPE-DROPPED**.

**Kept**:
- A **lightweight regime-validation capability** — distinct from a
  strategy backtester (see Regime validation, below).
- Versioned model registry — repurposed to store regime configs (JSON
  rule sets v1, v2, …) and later ML artifacts.
- Calculator `model_id` / `model_version` tagging per pre-trade calc.
- Comparison + combined analytics views.

## Regime classifier architecture

### The interface seam (the load-bearing decision)

```
classify(signals) -> RegimeResult{ label, multiplier }
```

- One stable interface. Position sizing consumes `RegimeResult` and never
  knows which implementation produced it.
- Default `multiplier = 1.0`; the regime result overrides it.
- The only thing that walls out ML later is hardcoding the
  rule-interpreter into the sizing path. Defining the interface is the
  insurance.
- **`signals` is per-model, not a fixed shape.** Each regime model
  declares what it consumes. The output side (`RegimeResult`) stays
  stable; the input side stays flexible. **The extensibility burden
  therefore lives in the feature-computation layer**, not the interface —
  when a model needs `rolling_vix_30d`, something must compute it. "Add
  ML" means "extend the feature layer," not "change the interface."

### Stage A — JSON rule interpreter (current / MVP)

- Rule-based thresholds (VIX, FRED 10Y/HY, BTC rvol, OI change, funding
  rate) stored as **JSON**, run by a small (~100-line) interpreter.
- Versionable, diffable, testable, inspectable. **No code execution.**
- Implementation #1 behind the interface.

Example shape:

```json
{
  "regime": "RISK_OFF",
  "when": { "vix": ">30", "hy_spread": ">5" },
  "multiplier": 0.5
}
```

### Stage B — ML implementation (end-phase, after rule-based validation)

- Implementation #2 behind the **same** interface. **Built only after the
  two-track validation shows rule-based regime sizing actually helps** —
  don't optimize a thing not yet shown to be worth doing.
- Storage: **model artifacts** (ONNX / joblib / weights) + a manifest —
  **not** a Python workspace and **not** stored arbitrary code.
- An inference call returns the same `RegimeResult`. No change to the
  sizing consumer.

### Explicitly NOT building

- **Python workspace / stored-arbitrary-code execution.** Executing
  stored Python is the most dangerous option and safe execution needs
  real sandboxing — unjustified for threshold rules; the ML case is
  covered by model-artifacts-plus-inference instead.

## Regime validation (the foundation)

The question the whole subsystem exists to answer: **does regime-aware
sizing improve risk-adjusted outcomes, or is it noise?** Two mechanisms,
used in sequence.

### 1. Historical counterfactual re-sizing (screening)

Replay **real past trades** through a candidate regime model: for each
historical trade, compute the multiplier the model would have assigned at
that trade's timestamp, re-scale the trade's P&L, compare.

- Lighter than a backtest — no entry/exit simulation, no look-ahead-bias,
  no fill modeling. Valid because the multiplier only scales size, and
  P&L scales linearly with size at retail volume.
- **Hard dependency**: regime signals (or regime state) must be available
  at each historical trade's timestamp. If the engine logs regime state
  per trade, this is free; otherwise backfill macro history
  (VIX / FRED / funding all have clean history — doable, but real work).
- **Use for screening only.** Tuning a model to look good on past trades
  is curve-fitting. Replay picks candidates fast; it does not promote
  them.

### 2. Forward two-track (out-of-sample confirmation)

Going forward, log **two P&Ls per trade**: the actual regime-sized P&L
*and* the counterfactual x1-default-sized P&L. Over time this is a clean
A/B — same trades, two sizing rules — answering "did scaling down in
risk-off regimes save more than it cost?"

- Unconfounded: identical trades, only size differs.
- Slow: signal accumulates only as trades occur across varied regimes; at
  discretionary cadence, expect months before it's statistically
  meaningful. Plan for a slow read, not a quick verdict.

### Promotion discipline

**Screen on history, promote on forward.** A candidate model earns a
place on the historical leaderboard cheaply; it earns *live* status only
after forward out-of-sample data confirms it holds up. This is the
shadow → A/B → live idea, kept precisely because the historical
leaderboard alone is a curve-fitting machine.

## Analytics

A **unified analytics surface**, with a **regime sub-section** that
compares models.

- **Multi-P&L comparison** — one column per candidate model + x1-default
  baseline + actual. Computing each model's multiplier across trade
  history is cheap once signals are stored (run the JSON interpreter per
  trade), so a **model leaderboard** is nearly free.
- **Dual-P&L logging is required, not optional** — the forward two-track
  (actual regime-sized P&L + x1-equivalent P&L per trade) must be logged
  at trade time, or the comparison can't be reconstructed later.
- **Comparison view** — backtest vs live by regime, *with the confound
  named*: external (MultiCharts) results don't carry the engine's regime
  multiplier, so that axis compares strategy-sans-regime against
  live-with-regime. The clean regime read comes from the multi-P&L on
  identical trades (above), not from the external-vs-live axis.
- **Forward-cadence pacing** — a reminder to re-run external backtests on
  cadence + storage of those results. Not in-engine walk-forward; named
  honestly so it isn't expected to do more.

## Storage model — what we store

1. **Algorithm** — regime classifier: JSON rule set (Stage A) / model
   artifact + manifest (Stage B), under the versioned registry.
2. **Connections** — data sources (yfinance, Deribit option gamma
   exposure, etc.) via the existing adapter / connection infrastructure.
3. **Per-trade regime state + signals** — required so historical
   counterfactual re-sizing works (see Regime validation §1).
4. **External backtest results** — ingested via the converter.

## External backtest + results converter

### Backtesting (external)

- **MultiCharts first.** vectorbt / backtrader converters added later.
- The engine never runs strategy backtests.

### Results converter (separate subsystem from the classifier)

- Ingests external backtest output → engine storage.
- **MultiCharts format first.** Design against a *real sample export*
  before building — one sample file dictates the schema.
- One source first; a multi-source converter risks a
  lowest-common-denominator schema — defer until a second source is
  actually needed.

### Drift risk (regime-logic sync)

If regime rules are also expressed in MultiCharts (PowerLanguage) for
external testing, that's a manual re-expression = drift risk. Mitigation:
keep the live classifier rule-based and simple while it's the source of
truth, so the JSON ↔ external match stays verifiable.

## Open questions

1. **Per-trade signal/regime logging** — **RESOLVED (Task 156
   investigation, 2026-05-23; CAVEATS (c) + (d) subsequently CLOSED by
   T157 + T163 + T165 + T166 — see "Build order" below). Verdict:
   PARTIAL → counterfactual replay feasible via timestamp join; no
   signal-backfill prerequisite under the normal case.**

   What IS persisted:
   - `regime_signals` ([core/database.py:297-306](core/database.py))
     stores all 6 raw signals (vix_close, us10y_yield, hy_spread,
     btc_rvol_ratio, agg_oi_change, avg_funding) keyed by
     `(signal_name, date)`. Day granularity.
   - `regime_labels` ([core/database.py:308-314](core/database.py))
     stores per-date label + mode + `signals_json` snapshot. Written by
     `classify_range()` ([core/regime_classifier.py:204](core/regime_classifier.py)).

   What is NOT persisted on the trade-side:
   - `pre_trade_log` ([core/database.py:71-104](core/database.py)) has
     NO regime_label / regime_multiplier / signal columns.
     `insert_pre_trade_log` ([core/db_trades.py:100-161](core/db_trades.py))
     writes none even though the calc dict carries `regime_multiplier`
     + `apply_regime_multiplier` from `risk_engine.py:473-474`.
   - `fills` ([core/database.py:381-402](core/database.py)) — same.
   - Only `backtest_trades.regime_label` exists
     ([core/database.py:274](core/database.py)); that's backtest scope.

   Trade ↔ regime linkage: **timestamp-join only**.
   `date(pre_trade_log.timestamp)` joins `regime_labels.date`;
   `date(fills.timestamp_ms / 1000)` joins the same.

   Counterfactual re-sizing of a NEW model on past trades — feasible
   because:
   - Raw signals are in `regime_signals` keyed by date.
   - Each trade timestamp resolves to a date → joins one signal-row
     per signal_name → feeds a new model's threshold-set → derives a
     new (label, multiplier) → re-sizes the past trade.
   - No new backfill needed IF `regime_signals` already covers the
     trade-date range.

   Caveats (don't block counterfactual; document for the multi-P&L
   leaderboard's footnote):

   a. **Day-granularity floor.** A trade at 14:30 UTC and a trade at
      03:00 UTC on the same day get the same regime label. Acceptable
      because the underlying signals (yfinance daily, FRED daily,
      Binance funding 8h aggregated) are day-resolution upstream.

   b. **Signal-window asymmetry**
      ([core/regime_fetcher.py:7-13](core/regime_fetcher.py)). VIX 30y,
      US10Y 50y, HY 25y — all macro signals fine. agg_oi_change /
      avg_funding only ~2-3 years (Binance API window). For trades
      older than that, only `mode="macro_only"` reconstruction works
      — same auto-fallback the live classifier already uses.

   c. **End-of-day snapshot vs trade-time snapshot.** Live trades go
      through `compute_current_regime()` which reads "most recent"
      signal values up to the day. If FRED published mid-afternoon
      between two trades on the same day, the persisted snapshot will
      not distinguish the two trades' read-times. Fine for
      counterfactual (the new model also uses end-of-day values); a
      minor drift if you wanted to audit live-engine sizing decisions
      at sub-day fidelity.

   d. **Live-classification fallback path leaves no trace.**
      `compute_current_regime()` falls back to live classification
      ([core/regime_classifier.py:273-292](core/regime_classifier.py))
      when no recent `regime_labels` row exists — this path returns a
      `RegimeState` but DOES NOT write to `regime_labels`. So a live
      trade made before any backfill has run has no persisted "label
      the engine actually applied" record. Counterfactual is unaffected
      (raw signals reconstruct it deterministically); auditing the
      live engine's exact decision history needs the operator to have
      run a backfill at least once covering the trade dates.

   Implication for the build-order steps below: step 1's "log
   per-trade regime state + dual P&L (actual + x1)" remains the right
   improvement to add — closes caveats (c) and (d) for future trades.
   It is NOT a prerequisite for replaying a NEW model on the EXISTING
   trade history; that works today via timestamp join.

   **Update (Task 167 re-sync, 2026-05-24):** caveats (c) + (d) are
   now CLOSED:
   - **(c) sub-day fidelity**: T165 (asymmetric hysteresis + live wire)
     + T166 (reading-id counting) make the live engine's exact decision
     reproducible at sub-day fidelity from the persisted regime_label /
     regime_multiplier / regime_mode / regime_stale columns on
     pre_trade_log — the multiplier stored is the AS-APPLIED effective
     value, not a re-derivation from now-mutable config.
   - **(d) fallback-path no-trace**: T157 (insert_pre_trade_log
     persistence of regime fields) closed the "live trade before
     backfill has no persisted label" gap. The fallback path's
     decision is now recorded per-trade regardless of regime_labels
     state.

   Dual-P&L (the OTHER half of step 1): closed by T167 as a derived
   query over closed_positions ⋈ pre_trade_log on calc_id — no new
   per-trade logging needed, because regime_multiplier persisted by
   T157+T165 IS the as-applied effective multiplier, and the
   linear-scaling assumption already accepted by this plan lets x1
   = actual_pnl / regime_multiplier compute correctly per trade.

## v3.0 — Deferred features (operator-decided)

### Drag-and-drop from calculator to Quantower

**Context:** scalping workflows benefit from sub-second value transfer.
Task 149 (FE-MED-033) introduced per-field click-to-copy on Calculator
Setup Summary outputs — operator clicks each value, switches focus to QT
order entry, pastes. Adds 2-3 keystrokes per value. At scalping volume
(>20 trades/day), the click overhead compounds.

**Approach:** browser-to-desktop drag-and-drop via Windows OLE delivers
`text/plain` payloads on drop. Quantower's custom order-entry controls
don't natively accept these. Requires C# plugin work to add `IDropTarget`
handlers on the QT order entry fields. Engine side gains
`draggable="true"` + a `dragstart` handler reusing the `copyField()`
raw-value lookup. The heavy lift is plugin-side.

**Effort:** medium — plugin C# work (3-5 sessions) + integration testing.

**Decision trigger:** build when scalping trade volume justifies the
plugin work; otherwise click-to-copy is sufficient and DnD stays parked.

**Plugin dependency:** DnD shipping would re-evaluate the
`core/platform_bridge.py` deprecation. If DnD never ships, the bridge
archive candidacy holds (see the module docstring).
